本文档面向希望深入理解 New_ORAD 内部实现的开发者，系统说明项目的设计思想、分层架构、代码组织、关键数据契约、核心算法、部署路径和二次开发约束。

本文以当前仓库代码为事实基线。功能状态分为：

```text
代码骨架 → 单元验证 → 离线验证 → 仿真闭环 → 实车验证
```

## 一、设计思想

New_ORAD 面向无标准车道、地形起伏明显、附着条件变化大且传感器扰动显著的非结构化越野环境。系统采用**模块化端到端（Modular E2E）**设计：学习模块负责从多模态观测生成轨迹，显式安全层负责将学习输出约束到车辆可执行范围。

核心思想包括：

1. **多模态 BEV 表征**：将多相机 RGB、LiDAR 和 IMU 历史编码到统一鸟瞰空间，使视觉语义、三维几何和车体姿态可以共同参与决策。
2. **IL + Model-Based RL**：先通过 Behavior Cloning 学习专家轨迹，再利用 RSSM 隐空间动力学和 Dreamer-style imagination 提升策略对分布偏移的适应能力。
3. **轨迹而非直接执行器输出**：策略输出 `[x, y, heading, velocity]` 轨迹，由安全层和控制器进一步处理，保留可解释约束和故障回退能力。
4. **Safety Envelope**：使用自行车模型、曲率、转向角/速率、纵向加速度、jerk、侧向加速度和 occupancy 碰撞检查形成硬安全边界。
5. **训练/部署解耦**：训练与验证使用 PyTorch，部署路径为 PyTorch → ONNX → TensorRT/C++，车辆控制通过 ROS 2/Ackermann 接口解耦。
6. **契约优先**：公共类型位于 `utils`；BEV 统一采用 `(B,C,H=y,W=x)`；正式评估强制有效 checkpoint；跨模块配置在启动时校验。
7. **分层验证**：CPU contract test 验证软件链路；CARLA/Gazebo/ROS2/TensorRT job 验证环境适配和物理行为；二者不能相互替代。
8. **先正确、再学习、后增强**：先关闭 frame/schema/sync/fail-safe 接口门禁，再建立 BEV、Affordance 与加权 BC 基线；在离线指标达标前不扩大 RSSM imagination 复杂度。

## 三、公共数据与坐标契约

### 3.1 核心数据类型

公共数据类定义在 `src/utils/types.py`：

| 类型 | 主要字段 | 语义 |
|---|---|---|
| `VehicleState` | x, y, yaw, speed, steering, pitch, roll, vx, vy, yaw_rate, accel_z | 世界系平面位姿 + 车体系状态 |
| `Waypoint` | x, y, yaw, speed, steering, t | 一条轨迹中的离散状态 |
| `Trajectory` | `list[Waypoint]`, frame, timestamp | 带坐标系与时间戳的策略候选或安全重积分轨迹 |
| `OccupancyGrid` | data, resolution, origin, thresholds | 二维概率占用网格 |
| `BEVFeature` | bev, occupancy, imu_state, metadata | 感知层输出 |
| `SensorPacket` | images, point_cloud, imu, timestamps | 基础公共传感器容器 |
| `Observation` | timestamp, simulator_frame, images, point_cloud, imu_history, ego_state, per-sensor frames/timestamps | 在线模型入口的严格同步契约 |
| `AffordanceOutput` | feature, traversability, roughness | BEV 辅助地形表征接口 |

`OccupancyGrid.origin=(x,y,yaw)` 表示 cell `(0,0)` 的世界位姿。查询时先执行世界系到 grid 局部系的逆旋转：

```text
dx = x_world - origin_x
dy = y_world - origin_y

x_local =  cos(yaw)·dx + sin(yaw)·dy
y_local = -sin(yaw)·dx + cos(yaw)·dy

col = floor(x_local / resolution)
row = floor(y_local / resolution)
```

网格外位置按占用处理，这是安全层的保守策略。

### 3.2 Tensor shape

```text
images      (B, N_camera, C=3, H_image, W_image)
points      (B, N_point, 4)       [x, y, z, intensity]
imu         (B, T, 6)             [ax, ay, az, gx, gy, gz]
attitude    (B, 3, 3)             body → gravity-aligned/world rotation
bev         (B, C_bev, H_bev, W_bev)
occupancy   (B, 1, H_bev, W_bev) values in [0,1]
trajectory  (B, N, 4)             [x, y, heading, velocity]
```

BEV 行列必须遵循：

```text
H / row ← y range
W / col ← x range
flat index = row * W + col
```

### 3.3 Frame 约定

- `CoordinateFrame` 只允许 `ego` 与 `world`；ego 为 x 前、y 左、z 上，长度/角度使用 SI 与 rad。
- `VehicleState.x/y/yaw`：world frame。
- 策略默认输出 ego-relative trajectory：x 前、y 左、heading 相对当前 yaw。
- `utils.frames` 提供点与 `Trajectory` 的 ego↔world 双向变换，并保留 frame/timestamp；非法 shape、NaN/Inf 或未知 frame 直接拒绝。
- LiDAR 构建的 occupancy 使用 ego pose 设置 world origin/yaw，使 world trajectory 可以正确查询局部栅格。
- CLI 可用 `--policy-frame world` 处理直接输出世界坐标的模型，但训练和 checkpoint 必须与该约定一致。

`Observation` 要求 camera 与 LiDAR simulator frame 完全一致、IMU 为 `(T,6)`、所有数组和时间戳 finite。它同时计算最大 frame skew 与时间 skew，供 `SafetySupervisor` 做运行时门禁。

### 3.4 跨模块配置契约

`configuration.system.load_system_stack` 严格读取 `configs/system.yaml`，拒绝未知/缺失 section 或 key，并从物理范围/resolution 派生 BEV H/W。它一次性生成 perception、policy、safety、controller、closed-loop、affordance 和 domain-randomization 配置。

随后 `utils.contracts.validate_stack_configs` 在闭环启动时检查：

- perception BEV channels/H/W 与 policy 输入一致；
- IMU channels/steps 一致；
- sim BEV range/resolution/point count 与 perception 一致；
- safety 与 controller 的 wheelbase、steering、accel、lateral accel 一致；
- sim 与 safety 的控制周期一致。

不一致时直接抛出 `ValueError`，避免错误配置进入闭环。

## 四、感知模块：多模态 BEVFusion

感知结构采用“各模态独立进入统一 BEV，再进行轻量融合”的边界：camera LSS
不以 LiDAR point 作为 query，LiDAR PointPillars-lite 也不依赖图像。两路输出
shape 对齐后由 `ModalityAwareBEVFuser` concat + Conv 融合，IMU 历史作为全局
BEV conditioning 加入。

`modality_mask (B,2)` 固定按 `[camera_valid, lidar_valid]` 排列。当前在线契约
要求每个样本两项均为 `True`；Camera 或 LiDAR 任一缺失、空输入、shape 错误或
含 NaN/Inf 时，整次 BEV 融合直接无效，由闭环上层进入最大制动，不再执行
camera-only/lidar-only 降级。`None` 仅表示两路数据已通过前置校验；不表示可以
绕过传感器健康检查。该变更保持 concat-conv 权重键和 ONNX 四输入张量路径兼容。

### 4.0 前模型传感器健康门禁

`utils.sensor_health.SensorHealthGate` 位于 simulator/replay/ROS adapter 与
`Observation` 之间，只依赖公共配置和 NumPy。它返回 Camera/LiDAR/IMU 三模态
有效性、frame、reference timestamp、最大 age/skew、稳定原因枚举，以及固定
`[camera_valid, lidar_valid]` mask。Runner 只有在三模态均有效时才构造
`Observation` 并调用 BEVFusion；否则直接记录原因、生成 emergency trajectory
并输出最大制动。

Camera 检查 count/shape/uint8/finite、黑屏、过曝、冻结和时间同步；LiDAR 在
padding 前检查 shape/finite/empty/点数/有效点比例/坐标范围/重复点与重复帧；
IMU 检查 `(T,6)`、完整 frame/timestamp 窗口、频率、量程和相邻步跳变。标定版本
必须与唯一 YAML 一致。当前无 IMU 降级控制器，因此 IMU 无效也采用保守急停。

跨帧冻结摘要在 episode 开始时 reset；只有 frame/timestamp 前进而内容连续相同
才累计。该软件判定已达到 CPU offline verified，但真实场景中静止画面、遮挡、
低纹理和传感器噪声的误拒绝率仍需 recorded replay 与 CARLA Stage 1B 标定。

Stage 1B Task 2 增加独立的 normal-stream evaluator，在不调用任何模型的条件下
对 1000+ CARLA ticks 统计 false rejection、age/skew 分布、frame/IMU continuity
和 health latency。CARLA reference timestamp 必须来自同 tick world snapshot 的
`elapsed_seconds`；不得从可能带非零起点的 frame counter 乘以 `dt` 推导。

### 4.0.1 Recorded CARLA health-first replay

`replay.carla_dataset.CarlaRecordedEpisode` 只接受带 `_SUCCESS` 的 episode，校验
schema、已声明 Canonical 字段、严格递增 frame/timestamp、相对路径边界、PNG/NPY
shape/dtype/finite 和 calibration。历史 manifest 缺字段时只能显式启用 legacy
provenance-gap 模式；计算出的当前文件 hash 不得伪装为采集时已经记录的 provenance。

```text
raw recorded Camera/LiDAR/IMU
  → SensorHealthGate(raw LiDAR, before padding)
  ├─ invalid → no Observation / no model → emergency trajectory → max brake
  └─ valid → Observation(canonical LiDAR)
             → calibration-aware BEVFusion
             → HybridPolicy
             → SafetySupervisor/SafetyFilter
             → PurePursuit offline command
```

Camera 输入固定 `[1,3,3,192,192]`，LiDAR `[1,256,4]`，IMU `[1,10,6]`，
mask 固定 `[[true,true]]`。相机外参将 pinhole optical frame 先变换到 CARLA
`x-forward/y-right/z-up`，再变换到 New_ORAD `x-forward/y-left/z-up`。随机网络只有
显式 `--allow-random-models` 才能运行；其 artifact 永远保存
`model_performance_valid=false` 与 `closed_loop_acceptance_valid=false`。

### 4.1 Camera 分支

每台相机经过三层轻量 CNN，下采样得到特征图；1×1 depth head 为每个像素预测离散深度概率：

```text
image (B·N,3,H,W)
  → CNN feature (B·N,Cf,Hf,Wf)
  → softmax depth (B·N,D,Hf,Wf)
  → feature × depth probability
  → lifted feature (B,Cf,N·D·Hf·Wf)
```

初始化时使用相机内参 K 和 cam→ego 外参 E 构建静态 frustum。对像素中心 `(u,v)` 和深度 `d`：

```text
Xc = d · (u-cx)/fx
Yc = d · (v-cy)/fy
Zc = d
p_ego = E · [Xc,Yc,Zc,1]
```

随后按 BEV 网格计算 row/col，并用 `scatter_add_` 将所有相机特征累加到 BEV。

### 4.2 LiDAR 分支

点云首先 pad/truncate 到静态 `num_points`，同时生成 valid mask。每点经过 MLP：

```text
[x,y,z,intensity] → Linear/ReLU → Linear/ReLU → pillar feature
```

若提供 attitude，则用 batched einsum 旋转 xyz。有效点计算 BEV cell 后通过静态 scatter 聚合：

```text
index = row * bev_w + col
bev_flat.scatter_add(dim=cell, index, point_feature)
```

固定点数服务于 ONNX/TensorRT 静态 shape。当前超长点云使用确定性前 N 点截断；工程部署建议替换为近场优先或体素分层采样。

### 4.3 IMU 分支与融合

IMU 历史 `(B,T,6)` 经过 GRU，末隐状态线性投影到 `C_bev`，作为全局动力学偏置广播到 BEV：

```text
camera BEV ─┐
             ├─ concat → Conv → ReLU → Conv → ReLU ─┐
LiDAR BEV ──┘                                        + IMU bias → fused BEV
```

融合 BEV 再经过 `Conv2d(C_bev,1)` 和 sigmoid 得到 occupancy 概率头。

### 4.4 当前限制

- 当前网络是验证架构和数据流的轻量实现，不是经过越野数据训练的量产感知模型。
- Canonical CARLA replay 使用 `system.yaml` 中由真实 episode calibration 提升的
  三路内外参；模型默认合成标定只允许独立开发测试，不能用于真实 replay 声明。
- Occupancy head 已实现代码和 shape/range 测试，但尚无监督数据或精度指标。
- `Observation` 已在 CARLA runner 与 recorded CARLA replay 中成为强制入口；ROS 2
  与训练 dataloader 尚未统一到同一 schema。

### 4.5 Terrain Affordance v1

`src/affordance/terrain.py` 在共享卷积编码器后输出两个独立栅格头：

```text
BEV → shared encoder ─┬→ sigmoid traversability ∈ [0,1]
                     └→ softplus roughness ≥ 0
```

训练 loss 为带 valid mask 的 BCE 与 L1 加权和。`roughness_target_from_imu` 可按去均值后的垂向加速度 RMS 和车速生成弱标签，并使用 `speed_epsilon` 避免零速度发散。该模块的 shape、范围、mask、反向传播和异常输入分支已有单测；但尚无真实地形标签或 F1/IoU，`configs/system.yaml` 中默认关闭，不能用作安全硬判据。

## 五、世界模型与混合策略

### 5.1 PolicyEncoder

BEV 经过三层 stride=2 卷积和全局池化；IMU 经过独立 GRU。二者拼接后由 MLP 得到 observation feature：

```text
BEV → Conv(32) → Conv(64) → Conv(128) → GAP → enc_hidden
IMU → GRU → enc_hidden
concat → MLP → hidden_dim
```

编码器支持单步 `(B,C,H,W)` 和序列 `(B,S,C,H,W)` 输入。

### 5.2 RSSM

状态由确定性隐变量 `h` 和随机隐变量 `z` 构成：

```text
h_t = GRUCell([z_(t-1), a_(t-1)], h_(t-1))
prior:     p(z_t | h_t)
posterior: q(z_t | h_t, observation_t)
```

训练模式从 posterior 重参数采样：

```text
z = mean_q + std_q · epsilon
```

评估/部署模式直接使用 `mean_q`，确保相同输入得到确定性轨迹。imagination 阶段使用 prior mean 推进。

### 5.3 World Model loss

世界模型总损失包括：

```text
L = L_obs_recon + L_bev_recon
  + reward_coef · L_reward
  + cont_coef · L_continue
  + kl_coef · L_balanced_KL
```

Balanced KL 分别阻断 prior/posterior 两侧梯度：

```text
KL_balanced = α·KL(stopgrad(q) || p)
            + (1-α)·KL(q || stopgrad(p))
```

当前默认 `α=0.8`。

### 5.4 Actor、Action Projection 与 Critic

- Actor：latent → MLP → 重复 horizon 次 → GRU decoder → `(B,N,4)` trajectory。
- ActionProj：将完整轨迹 flatten 后压缩到 RSSM action dimension。
- Critic：latent → scalar value。

BC 使用显式物理分量加权：

```text
L_BC = w_xy·MSE(x,y)
     + w_heading·MSE(heading)
     + w_speed·MSE(speed)
     + w_smooth·MSE(Δ²(x,y))
```

默认权重为 `1.0 / 0.2 / 0.2 / 0.05`，各分量独立返回以便实验审计。WorldModel loss 额外记录 prior/posterior 标准差，用于发现隐变量塌缩；默认 imagination horizon 从 15 收敛到 5，待短期预测和 BC 门禁达标后再扩展。

### 5.5 Dreamer-style imagination

从当前 posterior state 出发：

```text
latent_t → actor trajectory_t → action_proj a_t
         → reward_head r_t
         → critic V_t
         → continue_head c_t
         → RSSM prior next state
```

随后计算带 continue probability 的 lambda return，用于 actor 最大化回报、critic 回归目标。

### 5.6 越野奖励

`OffRoadReward` 包含四项：

```text
R = w_progress · R_progress
  - w_collision · R_collision
  - w_attitude · R_attitude
  - w_jerk · R_jerk
```

- Progress：位移在当前 heading 方向上的投影。
- Collision：使用 `grid_sample` 在 occupancy 上双线性采样；网格外按占用处理。
- Attitude：pitch/roll 变化率与超限量惩罚。
- Jerk：速度二阶差分平方惩罚。

当前 RSSM/WorldModel 类仍位于 `policy/hybrid_policy.py`，而 `src/world_model` 是目标独立包。拆包需同时处理 checkpoint key 和 API 兼容，尚未实施。

## 六、安全过滤与车辆控制

### 6.1 运动学自行车模型

使用后轴参考点和 Euler 离散：

```text
v_(t+1)   = clip(v_t + a_t·dt, 0, v_max)
x_(t+1)   = x_t + v_(t+1)·cos(yaw_t)·dt
y_(t+1)   = y_t + v_(t+1)·sin(yaw_t)·dt
yaw_(t+1) = yaw_t + v_(t+1)/L · tan(delta_t) · dt
```

模型负责控制限幅、单步推进、序列 rollout 和轨迹可行性重建检查。

### 6.2 曲率与侧向加速度

策略轨迹通常不带 steering，SafetyFilter 从 waypoint heading 差分估计曲率：

```text
kappa = wrap(yaw_(i+1)-yaw_i) / arc_length
```

若 waypoint 显式带 steering：

```text
kappa = tan(delta) / wheelbase
```

硬约束：

```text
|kappa| ≤ tan(delta_max)/L
|delta_t-delta_(t-1)| ≤ steering_rate_max·dt
a_y = v²·|kappa| ≤ lateral_accel_max
v ≤ sqrt(lateral_accel_max / |kappa|)
```

修正后的 steering/accel 通过自行车模型重新积分，得到 feasible-by-construction trajectory。

### 6.3 Occupancy 碰撞过滤

SafetyFilter 逐 waypoint 查询 OccupancyGrid，并按 inflation 半径检查邻域。遇到第一个 occupied cell 时截断其之前的安全前缀。

若最终轨迹为空，PurePursuit 返回：

```text
steering = 0
speed = 0
accel = max_decel
```

这是一条显式 fail-safe，而不是零油门零刹车滑行。

### 6.4 Pure Pursuit

动态前视距离：

```text
L_d = clip(L_0 + k_v·max(v,0), L_0, 12 m)
```

目标点在车体方向的夹角为 `alpha`，转向命令：

```text
delta = atan2(2L·sin(alpha), L_d)
```

目标速度同时受 waypoint speed、车辆最大速度和侧向加速度约束；纵向使用 P 控制并限幅。

### 6.5 CasADi 状态

`SafetyFilter.optimize_casadi` 当前仍是占位接口。即便安装 CasADi，也回退到确定性投影；因此当前系统不应被描述为已经实现 NMPC。

### 6.6 SafetySupervisor 状态机

`SafetySupervisor` 位于学习策略与确定性安全过滤之间，先验证 trajectory 数量、frame、finite、速度范围，以及 sensor age/skew 和模型时延：

```text
valid + no intervention     → NORMAL
valid + safety correction  → DEGRADED
missing/short/frame error/NaN/Inf/timeout/skew → EMERGENCY_STOP
```

急停输出为空但带正确 frame/timestamp 的 `Trajectory`，由 Pure Pursuit 映射为 `max_decel`。1000 条合成轨迹的 M0 CPU 门禁会周期注入 NaN，并断言所有无效样本均进入最大制动、正常样本不误触发。

## 七、CARLA 闭环与域随机化

### 7.1 传感器同步

`CarlaSensorStack` 为每台相机维护独立队列，LiDAR 记录 frame ID，执行 `world.tick()` 后等待同 frame 的全部 camera 和 LiDAR 数据，超时返回 `None`。IMU 历史保留 frame/timestamp/accel/gyro 并打包为 `(T,6)`；同 frame world snapshot 的 `elapsed_seconds` 作为健康门禁 reference timestamp，runner 将 camera、LiDAR 和最新 IMU 时间戳写入 `Observation`。

每个 episode 开始时清零碰撞次数和最大冲击量，避免上一回合污染指标。

### 7.2 闭环 runner

```text
sensor tick
  → Observation schema/frame/skew validation
  → canonicalize LiDAR
  → IMU gravity alignment
  → perception
  → policy
  → ego trajectory to world
  → select occupancy: lidar | learned | max-fused
  → SafetySupervisor
  → safety filter
  → pure pursuit
  → CARLA VehicleControl
  → metrics
```

正式 CLI 必须同时提供有效 `--perception-ckpt` 和 `--policy-ckpt`，并使用 `strict=True` 加载。随机权重只能通过显式 `--allow-random-policy` 用于开发冒烟。

默认安全占用源为 `lidar`。`learned` 将 `BEVFeature.occupancy (1,1,H,W)` 转为带 world origin/yaw 的 `OccupancyGrid`；`fused` 对 LiDAR 与 learned probability 逐 cell 取最大值。learned 数据缺失、shape/finite/range 不合法时 fail-safe 制动。

sensor timeout、Observation/预处理异常、感知异常或策略异常都在 runner 内转换为显式最大制动；模型返回但超过时延门槛、输出 NaN/Inf/错误 frame/过短轨迹则由 `SafetySupervisor` 拒绝。

### 7.3 指标

- success：到达目标且无碰撞。
- collision rate：发生至少一次碰撞的 episode 比例。
- progress：相邻 world position 的累计距离。
- pitch/roll max 与报警次数。
- lateral acceleration：`|v·yaw_rate|`。
- collision impulse：CARLA normal impulse 模长。
- safety intervention/emergency-stop 次数与比率。
- raw policy risk 与 post-safety risk，用于区分策略本身和安全层后的风险。

SDD 闭环门槛为成功率 >90%、碰撞率 0、姿态过载报警 0；当前真实环境用例仍处于 skip 状态。

### 7.4 Domain Randomization

`sim/domain_randomization.py` 提供：

- 按 seed 可复现的 episode manifest。
- tire friction、vehicle mass、LiDAR sigma/dropout、suspension damping 采样。
- 不修改输入的 LiDAR xyz Gaussian noise 和 dropout。

参数采样和点云增强已单测；CARLA/Gazebo 物理参数注入仍需对应环境验收。

## 八、ROS 2 与部署

### 8.1 ROS 2 控制节点

`VehicleControlNode`：

- 订阅 `/orad/safe_trajectory`。
- 订阅 `/carla/ego_vehicle/odometry`。
- 定时执行 Pure Pursuit。
- CARLA 发布 `AckermannDrive`。
- Gazebo 发布 `AckermannDriveStamped`。

当前轨迹消息为 `[x,y,yaw,v]*N` 的 `Float32MultiArray`。正式工程建议定义带 `Header`、`frame_id`、schema version 和 waypoint 数量的自定义消息。

### 8.2 ONNX 导出

感知模型输入：

```text
images, points, imu, attitude → bev
```

策略输入：

```text
bev, imu → trajectory
```

导出使用 opset 17，仅 batch 动态。导出强制在 CPU 上执行；`onnx.checker` 失败会作为硬错误传播，而不是打印后继续。

当前测试证明模型可以导出并通过 checker，但尚未完成 ONNX Runtime/TensorRT 数值一致性和目标硬件时延验证。

### 8.3 TensorRT C++

`orad_trt_engine.hpp` 定义：

- ONNX build / serialized engine load-save。
- FP32/FP16/INT8 precision 枚举。
- optimization profile 与动态 batch。
- binding introspection。
- CUDA stream 异步 Infer。
- perception + policy `PolicyPipeline`。

当前只有 API 头文件，没有 `.cpp`、CMake、calibrator 或编译测试，属于代码框架而非已完成 runtime。

## 九、模块连接与故障路径

### 9.1 正常路径

```text
CARLA/ROS sensors
  → synchronized arrays
  → BEVFeature
  → deterministic trajectory
  → world-frame Trajectory
  → feasible safe prefix
  → ControlCommand
  → Ackermann/CARLA command
```

### 9.2 失效路径

| 故障 | 当前行为 |
|---|---|
| sensor frame 超时 | 输出最大制动并结束 episode |
| sensor timestamp skew 超限 | `EMERGENCY_STOP`，输出最大制动 |
| Observation/模型异常 | 捕获异常，输出最大制动并结束 episode |
| 模型输出 NaN/Inf、frame 错误或过短 | `SafetySupervisor` 拒绝并急停 |
| checkpoint 缺失 | 正式评估启动失败 |
| checkpoint shape/key 不匹配 | strict load 失败 |
| 配置漂移 | `validate_stack_configs` 启动失败 |
| YAML 未知/缺失字段 | `load_system_stack` 启动失败 |
| 请求 learned occupancy 但缺失/非法 | 输出最大制动并结束 episode |
| occupancy 查询越界 | 按 occupied 处理 |
| 首 waypoint 碰撞 | safe trajectory 为空 |
| safe trajectory 为空 | 最大减速度命令 |
| CasADi 不可用 | 使用确定性运动学投影 |

生产部署仍应增加 watchdog、错误状态发布、制动确认和系统级 emergency-stop 仲裁。

## 十二、扩展与二次开发指引

### 新增传感器

1. 扩展 `SensorPacket` schema，明确 shape、单位、frame 和 timestamp。
2. 在 perception 新增独立 encoder，不让 adapter 依赖 policy。
3. 更新 fusion channels 和 ONNX 静态输入。
4. 增加空输入、不同步、NaN/Inf、batch/device 边界测试。

### 修改 BEV 范围或分辨率

必须同步：

- `BEVFusionConfig`。
- `HybridPolicyConfig.bev_h/bev_w`。
- `OffRoadRewardConfig`。
- `ClosedLoopConfig`。
- `configs/system.yaml`。
- 训练数据标签和 checkpoint metadata。

启动时 `validate_stack_configs` 会检查大部分关键漂移。

### 更换策略结构

必须保持 trajectory tensor `(B,N,4)` 或同步修改：

- `policy_trajectory_to_waypoints`。
- SafetyFilter 曲率估计。
- ROS trajectory message。
- ONNX output 和 TensorRT binding。
- BC fixture、frame 和物理约束测试。

### 更换车辆平台

统一修改 wheelbase、steering/rate、accel/decel、lateral accel，并确保 safety/controller/CARLA mapping 一致。不得只修改控制器而保留旧安全模型。

### 实现 CasADi NMPC

先编写 Red tests：约束满足、不可行问题回退、occupancy avoidance、求解超时、与 deterministic projection 的兼容接口；随后实现 OCP，并保留无 CasADi 环境下的纯 NumPy路径。

### 实现 TensorRT Runtime

顺序建议：

1. ONNX Runtime 与 PyTorch batch 1/2 数值对齐。
2. TensorRT parser/build 冒烟。
3. FP32/FP16 精度差异。
4. engine cache 与动态 profile。
5. CUDA stream 和端到端时延。
6. 闭环 ADE/碰撞指标回归。
7. 达标后再引入 INT8 calibrator。
